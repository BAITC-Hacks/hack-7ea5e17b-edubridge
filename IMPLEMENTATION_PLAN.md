# Implementation plan — Agentic AI для прогнозирования ВЭС

Дата: 23 сентября 2026. План для команды из трёх человек. Пункты ниже описывают будущую реализацию, а не уже готовые возможности.

Обновление участника №1: реализованный статус и проверяемые команды находятся в README. Для интеграции с предложением участника №2 (PR №2) внутренний `valid_time` выбран концом часового интервала; replay в 23:00 Asia/Almaty включает 29 выдач от 31 января до 28 февраля. Это не подтверждение исходной временной семантики SCADA. Точные контракты: `docs/model-integration.md`, `docs/api-contract.md`; реальная погодная проверка: `docs/weather-source.md`.

## 1. Задача и критерии результата

По [ТЗ Самрук-Казына](https://docs.google.com/document/d/1Fn5IJoj87Fx7IAknG26zkfX8c0eq7feCujd0m66PCgY/preview?tab=t.0) нужно:

1. Использовать историю работы ВЭС с марта 2023 по 31 января 2026 включительно.
2. Самостоятельно получать открытые архивные прогнозы погоды по координатам двух турбин.
3. Прогнозировать почасовую выработку на 24–48 часов.
4. Воспроизвести ежедневные расчёты начиная с 31 января для тестового периода 1–28 февраля 2026.
5. Реализовать полный цикл агента: погода → подготовка → модель → прогноз → анализ → пересчёт при обновлении входов.
6. Использовать только сведения, доступные в исторический момент расчёта. Фактическая погода и более поздние выпуски прогноза не могут заменять архивный прогноз.

| Критерий технического отбора | Баллы | Что предъявляем |
| --- | ---: | --- |
| Соответствие задаче, работоспособность | 25 | Replay февраля, почасовые горизонты, фактический источник погоды |
| Техническая реализация | 25 | Работающий цикл агента, взаимодействие компонентов, корректные временные ограничения |
| README и воспроизводимость | 25 | Чистая установка, доступные данные/артефакты, команды запуска и проверки |
| Ценность и применимость | 15 | Понятный прогноз, ограничения, источник, контроль качества |
| Развитие и оригинальность | 10 | Обоснованный способ обновления, масштабирования и анализа неопределённости |

В ТЗ не заданы обязательная метрика ошибки, её вес, формат submission, час ежедневного выпуска, трактовка нормализации мощности и часовой пояс исходного датасета. Не выдаём выбранные нами значения за требования организатора.

| **№2: данные и ML** | `feat/forecast-model` | `src/wind_agent/data/`, `features/`, `model/`, `evaluation/`; `tests/model/`; `docs/model-card.md` | Адаптер датасета, baseline, обученная модель, временная валидация, прогнозный интерфейс |
| **№3: интерфейс и демо** | `feat/dashboard-demo` | `ui/`; `tests/ui/`; `docs/demo.md`; `docs/pitch.md` | Интерфейс по общему контракту, графики, экспорт, статусы и сценарий демонстрации |

№1 согласует общие контракты и зависимости; №2 определяет смысл целевой величины и признаки; №3 отвечает за понятность пользовательского результата. Имена и GitHub-логины не требуются для этого распределения.

Чтобы не блокировать друг друга: №2 начинает с локального загрузчика и модели на train/validation; №3 — с явно помеченного fixture по контракту API; №1 — с получения реального исторического выпуска погоды. Fixture не используется как доказательство реального прогноза.

## 3. GitHub-процесс

Официальный remote: `https://github.com/BAITC-Hacks/hack-7ea5e17b-edubridge.git`.

- Все три ветки создаются от актуального `origin/main`.
- Каждый участник работает в своей ветке и преимущественно в своих каталогах.
- На одном компьютере нельзя одновременно переключать ветку общей рабочей папки для разных участников. Нужны отдельные клоны или git worktree внутри того же официального репозитория.
- Каждый законченный этап: содержательный commit, push в свою ветку, PR с base `main`.
- Минимум один другой участник просматривает код и доказательства проверки перед merge. Для интеграционных изменений №1 привлекает №2 или №3; чужие PR интегрирует №1 после проверки.
- Не делать прямые push в `main`, force-push, переписывание чужой истории или массовое форматирование чужих каталогов.
- Использовать обычный merge commit для сохранения истории по часам. Ветка после merge остаётся рабочей; следующий этап можно отправить новым PR из неё.
- Перед новой задачей подтянуть `origin/main` в рабочую ветку. Конфликты решать совместно с владельцем затронутых файлов.
- По правилам хакатона нужен подтверждаемый результат каждого часа. Практическая цель: push реального прогресса каждые 30–45 минут; пустые commits не заменяют результат.
- Запрет прямых push пока организационный: серверная branch protection не настроена. Доступ к admin-настройкам репозитория не предполагается.

Начало работы (заменить `<своя-ветка>` именем из таблицы):

```sh
git fetch origin
git switch <своя-ветка>
git merge origin/main
```

Если ветка существует только на GitHub, вместо `git switch` выше: `git switch --track origin/<своя-ветка>`.

```sh
git add <изменённые-файлы>
git commit -m "feat: describe completed change"
git push -u origin HEAD
```

В GitHub открыть PR: base `main`, compare — своя ветка. Первый PR — этот план; он не содержит работающего приложения. После его merge остальные участники подтягивают `main`.

## 4. Минимальная архитектура и стек

Предлагаемый стек для пятичасового MVP: Python 3.11, pandas, NumPy, scikit-learn, joblib; HTTP-клиент; FastAPI + Pydantic; Streamlit + Plotly. Версии фиксирует №1 после проверки совместной установки. Дополнительный движок чтения Excel добавляется только если его требует реальный датасет.

```text
Исторический выпуск погоды → проверка доступности → нормализация данных
                                                    ↓
История ВЭС → очистка → обучение/валидация → модель → почасовой прогноз
                                                    ↓
                              анализ качества → артефакт + API → UI
                                                    ↓
                     новые доступные входы → пересчёт новой ревизии
```

Минимальный агент — управляющий цикл с состоянием, инструментами и наблюдаемыми решениями. Он выбирает доступный исторический выпуск, вызывает загрузчик и модель, проверяет результат, повторяет запрос при временном сбое и пересчитывает изменившиеся входы. Просто отдельный вызов `model.predict()` не покрывает требование полного цикла.

LLM-анализатор — опциональный слой объяснения и выбора разрешённого действия по структурированным результатам. Он не генерирует числовой прогноз вместо модели и не меняет временные ограничения. Если его добавлять, №1 обеспечивает проверку без личной платной подписки участника. Не тратить время на многоагентную архитектуру до готовности одного полного сценария.

## 5. Общие контракты — согласовать в первые 15 минут

Внутреннее время — timezone-aware UTC; отображение — явно выбранная зона. Часовой пояс исходных данных и смысл timestamp (начало/конец часа) №2 сначала подтверждает по файлам. Не приписывать naive timestamp UTC автоматически.

### История турбины

`turbine_id`, `timestamp`, `wind_speed_ms`, `ambient_temperature_c`, `target_power_normalized`, `quality_flag`.

- Сохранить исходные значения и карту колонок. Не перезаписывать оригиналы.
- Уточнить, есть ли данные отдельно по двум турбинам или сразу по станции, границы нормализации и что означает «мощность на стороне линии».
- Нормализованную мощность не подписывать как MW/MWh. Суммарную мощность двух турбин рассчитывать только при известном масштабе и корректных весах. До этого показывать прогноз отдельно по доступным целям.

### Архивный прогноз погоды

`turbine_id`, `latitude`, `longitude`, `provider`, `weather_model`, `model_run_time`, `forecast_available_at`, `availability_basis`, `retrieved_at`, `valid_time`, `lead_hours`, `wind_speed_ms`, `wind_height_m`, `temperature_c`, `source_request`, `raw_sha256`.

`model_run_time` — инициализация погодной модели; `forecast_available_at` — когда этот выпуск можно было получить. Это разные моменты. Если источник не сообщает публикацию, явно записывать консервативное правило задержки и его основание; не представлять предположение как доказанный timestamp публикации.

### Результат прогноза

`schema_version`, `run_id`, `revision`, `issue_time`, `turbine_id`, `valid_time`, `lead_hours`, `prediction`, `target_unit`, `weather_model`, `weather_run_time`, `model_version`, `training_cutoff`, `data_quality`, `warnings`.

- Уникальный ключ внутри ревизии: `(issue_time, turbine_id, valid_time)`.
- `lead_hours` результата отсчитывается от `issue_time`; для погоды — от `model_run_time`. Не смешивать эти два горизонта.
- Все числа конечные, часовая сетка непрерывная, шаг — один час; диапазон мощности ограничивать только подтверждёнными границами целевой переменной.
- Интервалы неопределённости добавляются только после калибровки; их отсутствие честно обозначается.

### Интерфейс модели между №1 и №2

```python
train(history, weather_features, cutoff, config) -> ModelArtifact
predict(model_artifact, weather_frame, issue_time, horizon_hours) -> ForecastFrame
evaluate(predictions, observed, split_config) -> MetricsReport
```

Набор признаков, порядок колонок, пропуски, единицы и версия сериализации фиксируются в metadata модели. Не ожидать фактическую погоду или фактическую мощность из будущего в `predict`.

### API между №1 и №3 — проектируемые маршруты

| Метод | Маршрут | Контракт |
| --- | --- | --- |
| GET | `/health` | Статус сервиса и готовность модели/данных |
| POST | `/runs` | `issue_time`, `horizon_hours` (24/48), `turbine_ids`; ответ `run_id`, `status` |
| GET | `/runs/{run_id}` | Состояние, шаги агента, предупреждения, ошибка, ревизия |
| GET | `/runs/{run_id}/forecast` | JSON-массив записей результата по контракту выше |
| GET | `/runs/{run_id}/forecast.csv` | Те же записи в CSV |
| GET | `/evaluation` | Метрики валидации, временные границы и baseline; факт наличия test truth |

Состояния: `queued`, `fetching_weather`, `validating`, `forecasting`, `analysing`, `completed`, `failed`. Долгий запрос не блокирует UI: запуск возвращает ID, UI опрашивает статус. Для MVP достаточно локального файлового хранилища и одного процесса; распределённая очередь не требуется.

## 6. Участник №1 — агент, погода, интеграция

- [ ] Проверить один настоящий архивный выпуск за январь/февраль 2026 для обеих координат до выбора провайдера.
- [ ] Зафиксировать контракт и конфигурацию: координаты, источник, timezone, час выпуска, горизонт, train cutoff, политика доступности.
- [ ] Реализовать погодный адаптер: timeout, ограниченные retry, проверка схемы и единиц, cache исходных ответов и provenance.
- [ ] Выбирать последний допустимый выпуск по `forecast_available_at <= issue_time`, а не просто по дате файла.
- [ ] Реализовать управляющий цикл и журнал действий. При неполных данных — объяснимая ошибка или явно помеченный допустимый fallback; запрещена тихая замена на фактическую погоду.
- [ ] Подключить интерфейс модели №2, API и артефакты результата.
- [ ] Реализовать ежедневный replay с выдачами с 31 января и покрытием целевых часов февраля. Хранить каждый прогноз отдельно; не затирать пересекающиеся горизонты.
- [ ] Повторный запуск с теми же входами — идемпотентный. Новые допустимые входы — новая ревизия с указанием причины пересчёта. Событие обновления в replay также не может приходить из будущего.
- [ ] Реализовать содержательные тесты на утечку, выбор выпуска, идемпотентность, отказ провайдера и полный сценарий.
- [ ] Подготовить зависимости, `.env.example` без секретов, README и чистый запуск из свежего клона.

**Готово, когда:** одна команда выполняет реальный исторический расчёт и сохраняет прогноз с происхождением данных; replay формирует согласованное покрытие февраля; повторные запуски и ошибки контролируемы; UI подключается без ручных правок данных.

## 7. Участник №2 — данные, модель, доказательство качества

- [ ] Исследовать предоставленные файлы: схема, timezone, единицы, обе турбины, пропуски, дубликаты, диапазоны, выбросы и возможные простои/ограничения мощности.
- [ ] Подготовить воспроизводимый адаптер и отчёт качества. Не заполнять пропуски через границы train/validation и не интерполировать с использованием будущих наблюдений.
- [ ] Реализовать простой baseline — обученная на истории зависимость мощности от ветра; persistence допустим лишь там, где последний факт действительно доступен на момент выпуска.
- [ ] Первую модель построить компактно: регрессия/HistGradientBoostingRegressor, нелинейность скорости ветра, температура, календарь, идентификатор турбины. Сравнить с baseline на одинаковом временном split.
- [ ] Train/validation разделять по времени, без случайного перемешивания; preprocessing fit только на train. По возможности использовать несколько последовательных holdout-окон до февраля.
- [ ] Согласовать с №1 получение исторических прогнозных признаков для валидации. Оценку по фактической погоде обозначать отдельно как диагностическую: это не честная day-ahead-оценка.
- [ ] Если модель мощности учится на измеренном ветре, описать сдвиг между измеренным ветром у турбины и модельным ветром на заданной высоте; проверить калибровку на доступном архиве прогнозов до февраля.
- [ ] Подготовить MAE/RMSE в единицах цели и по горизонтам. Не обещать NMAE без определения знаменателя; не использовать MAPE как основной показатель около нуля мощности.
- [ ] Обучить итоговый артефакт только на доступной к соответствующему `issue_time` истории. Наличие в файле всех данных 31 января ещё не означает их доступность утром 31 января.
- [ ] Не добавлять фактическую выработку февраля в обучение или лаги replay, если организатор её не предоставил как допустимые на тот момент наблюдения.
- [ ] Сохранить model metadata, feature schema, split, seed, training cutoff и model card; раскрыть библиотеки и ограничения.

**Готово, когда:** №1 загружает модель и получает прогноз через согласованный интерфейс; baseline и модель сравнены без будущих данных; каждое заявленное качество подтверждено отчётом. Если факта февраля нет, test-метрики не вычисляются и не выдумываются.

PR №1 — план. Следом №1 создаёт общие контракты/каркас; №2 и №3 подтягивают их после merge. Затем небольшие PR по готовым этапам из каждой рабочей ветки. Не оставлять три несовместимые реализации до последнего часа.

## 10. Проверки временной корректности и воспроизводимости

- [ ] Для каждой строки погоды соблюдается `forecast_available_at <= issue_time`; выбранный выпуск существует, его исходный ответ сохранён.
- [ ] `model_run_time` не принимается за время публикации без оговорок.
- [ ] Обучение, нормализация, заполнение пропусков, подбор параметров и лаги не используют будущие сведения.
- [ ] Для каждого выпуска есть полный почасовой горизонт; ошибки/неполнота не превращаются незаметно в нули.
- [ ] Конфигурация фиксирует начало/конец часа и timezone. Отдельно проверены обе границы февраля и переходы суток.
- [ ] Перекрывающиеся прогнозы хранятся по origin/lead; способ выбора одной строки на тестовый час документирован и не выбирается по минимальной ошибке после просмотра факта.
- [ ] Replay покрывает 1–28 февраля в согласованной временной зоне. Февраль 2026 содержит 672 часовых интервала на одну цель без перехода DST; не требовать всего 672 строк от таблицы с несколькими выпусками/турбинами.
- [ ] Прогнозные часы марта, попавшие в 48-часовой горизонт конца февраля, хранятся отдельно от февральской оценки.
- [ ] Чистый запуск по README проверен другим участником. Демо cache должен содержать допустимые реальные архивные данные с provenance, не синтетическую замену.
- [ ] Секретов в git нет. Тестовые доступы или инструкции проверки доступны экспертам без личной подписки автора.

## 12. Приоритеты при дефиците времени

**P0:** реальная загрузка архивного выпуска; правильное время; baseline/модель; полный почасовой прогноз; ежедневный replay; журнал агента; рабочий UI; README и чистый запуск.

**P1 после P0:** улучшение модели, калибровка, демонстрация ревизий в UI, более подробная диагностика, несколько временных holdout-окон.

**P2 только после устойчивого результата:** ансамбль, калиброванные интервалы неопределённости, несколько погодных провайдеров, LLM-пояснения, дополнительные карты и деплой.

Если архив прогнозов не удалось получить, сообщить о блокере и зафиксировать частичную готовность. Historical Weather/reanalysis и случайные данные не закрывают требование ТЗ к архивным прогнозам.

## 14. Проверка открытых погодных источников

Предварительная оценка по официальной документации. Успешные реальные запросы за февраль ещё не выполнены; выбор провайдера остаётся задачей №1.

| Вариант | Что подтверждает документация | Что проверить до использования |
| --- | --- | --- |
| [Open-Meteo Single Runs](https://open-meteo.com/en/docs/single-runs-api) | Выбор конкретного `run`; ECMWF IFS HRES 9 km с 14.03.2024, остальные модели только с 02.04.2026 | Запросы начала/середины/конца февраля; состав признаков; время публикации; происхождение архива |
| [NCEI GFS 0.5°](https://www.ncei.noaa.gov/products/weather-climate-models/global-forecast) | Циклы 00/06/12/18 UTC, шаг прогноза 3 часа, около двух лет онлайн | Наличие конкретных файлов февраля, доступность GRIB, публикацию и стоимость реализации почасовой интерполяции |

Open-Meteo удобнее для быстрого MVP, но архив ECMWF в документации обозначен как **Cycle 49R1 hindcasts**. До проверки нельзя утверждать, что это в точности оперативный прогноз, доступный в прошлом. Если он пересчитан позднее и не удовлетворяет требованию ТЗ, выбрать подтверждённый архив оперативных выпусков либо получить разъяснение постановщика. Это не решается одной проверкой `run <= issue_time`.

[Historical Forecast](https://open-meteo.com/en/docs/historical-forecast-api) сшивает первые часы разных запусков и не должен автоматически трактоваться как один day-ahead выпуск. [Historical Weather](https://open-meteo.com/en/docs/historical-weather-api) содержит ретроспективную погоду; подстановка будущих фактических условий запрещена. [Previous Runs](https://open-meteo.com/en/docs/previous-runs-api) даёт фиксированные смещения относительно прогнозируемого времени, что требует отдельной проверки согласованности выпуска.

Глобальные модели обычно появляются спустя несколько часов после инициализации; задержку для выбранного продукта проверять отдельно. Использовать [описание метаданных обновлений](https://open-meteo.com/en/docs/model-updates), а не сегодняшний `retrieved_at` как время исторической доступности. Современная оценка задержки сама по себе не доказывает точную публикацию каждого исторического выпуска.

Почасовую интерполяцию трёхчасового GFS допустимо делать внутри одного доступного прогноза; не смешивать её с интерполяцией будущих фактических наблюдений.
