Сценарий на 3 минуты. Проверенные результаты приведены ниже со ссылками на артефакты; для отсутствующих измерений произносить «не измерено». Синтетический деморежим подтверждает работу интерфейса; его нельзя представлять как законченный прогноз реальной ВЭС.

Основной frontend — **JelAI**, React/TypeScript в `ui/web`; название объединяет «жел» (ветер) и AI. Streamlit сохранён как альтернатива. Логотип и иллюстрация ветропарка — оформление продукта; фон не изображает подтверждённую площадку и не передаёт телеметрию.

Эти результаты не заменяют проверку нового React-интерфейса. API с `config/demo.json` возвращает синтетический fixture через настоящий HTTP; эти проверки не подтверждают точность реального прогноза мощности.

В `main@6e4724e` был поставлен обученный пакет и отчёт: [model card](model-card.md), [validation.json](../models/wind-power-v1/validation.json), [описание `/evaluation`](evaluation-api.md). Ниже численные ML-результаты относятся к этому отчёту, а браузерные проверки JelAI фиксируются отдельно.

## 1. Проблема и результат — 30 секунд

«JelAI — это “жел”, ветер, и AI. Для планирования работы ВЭС нужен почасовой прогноз на ближайшие 24–48 часов. Мы строим систему для двух турбин, которая получает архивный прогноз погоды, рассчитывает выработку и показывает, откуда взялся каждый результат. Пользователь выбирает исторический момент выпуска, турбины и горизонт, затем получает график, таблицу и CSV».

Практическая ценность: прогноз и его ограничения находятся рядом. Можно проверить время выпуска, погодный источник, версию модели, качество входов и причину пересчёта, прежде чем использовать результат.

## 2. Как работает система — 45 секунд

```text
Архивный выпуск погоды → проверка временной доступности → признаки
                                                         ↓
История турбин → модель → почасовой прогноз → проверки → API → UI / CSV
                                                ↑
                        новые допустимые входы → новая ревизия
```

«Роль агента — управлять последовательностью действий, проверять доступность входов, обрабатывать сбои и сохранять причину обновления. Числа прогнозирует модель. Для исторического расчёта нельзя использовать сведения из будущего: ограничение относится и к обучению, и к выпуску погоды. Инициализация погодной модели и публикация прогноза — разные моменты».

Платформа содержит API, архивный погодный адаптер, цикл агента и подключённый пакет `models/wind-power-v1` в `config/archive-model.json`. Показывать как проверенные вместе только звенья, подтверждённые сохранённым сквозным запуском. UI отображает полученные metadata; сам экран не доказывает корректность архива или обучение без утечки.

## 3. Короткое демо — 60 секунд

1. Назвать источник: **встроенное демо UI**, **HTTP API с backend demo** или **HTTP API с архивным расчётом**. Для API показать `run_id` и режим сервиса. Backend demo обозначить как синтетический fixture, хотя соединение по HTTP настоящее.
2. Выбрать выпуск, турбины и 24 часа. Получить результат, показать состояние агента, график и таблицу. У backend demo единица `fixture_dimensionless`, предупреждение `SYNTHETIC FIXTURE`, а журнал находится в `events`; это тестовая безразмерная величина, не нормализованная мощность. `valid_time` — конец часового интервала.
3. Открыть происхождение данных: время выпуска, погодный run, версию модели, cutoff обучения, предупреждения и ревизию.
4. Показать экспорт CSV. Для повторного запуска в JelAI оставить параметры и снова нажать «Рассчитать прогноз»; «Обновить статус» только запрашивает состояние текущего выпуска. Встроенное демо создаёт искусственную ревизию. Реальный автономный monitor подтвердил `created → unchanged → new_issue`: повтор сохраняет ID и ревизию, следующий исторический выпуск получает новый ID и более свежую допустимую погоду. Revision 2 после изменения входов подтверждена fixture-тестами погоды и модели; реальный revised-weather и браузерный сценарий revision 2 не проверены. [Протокол](evidence/agent-monitor-integration.json), [запуск monitor](agent-monitor.md).

Подробные шаги и сценарии сбоев: [docs/demo.md](demo.md).

Метрики взяты из [отчёта модели](../models/wind-power-v1/validation.json), покрытие replay — из [сохранённой проверки команды](replay-validation.md). Январский holdout относится к модели, замороженной до этого периода, а не к финальному production-refit. Не выдавать эти числа за точность февраля.

Новый [протокол JelAI React](demo.md#протокол-проверки-jelai-react--23-сентября-2026) раздельно подтверждает синтетический и реальный архивный цикл с сохранёнными браузером CSV. Архивный запуск использует GFS от 31 января 12:00 UTC, доступный по принятой политике архива с 15:59:20 UTC, и `wind-power-v1` с cutoff 18:00 UTC. Это локальная интеграция, а не измерение точности февраля или публичное развёртывание. `data_quality=warning` и ограничения model card сохраняются.

Исторический протокол Python/Streamlit с `run_id`, версиями Python и командами: [demo.md](demo.md#протокол-проверки--23-сентября-2026). CSV проверен Python API-клиентом; в прежнем браузерном UI проверено нажатие кнопки, сохранение файла на диск не подтверждено.

## 5. Воспроизводимость и следующий шаг — 15 секунд

«JelAI запускается из `ui/web` командами `npm ci` и `npm run dev`, по адресу `http://127.0.0.1:5173`. Встроенное демо не требует backend или аккаунта автора. Архивный API подключает готовую модель и получает доступную на исторический момент погоду; frontend обращается к нему через `/api`».

Из корня репозитория с окружением Python 3.11:

```sh
.venv/bin/python -m pip install -e '.[dev,weather,model]'
.venv/bin/python -m wind_agent --config config/archive-model.json serve
```

Синтетическая альтернатива после остановки архивного API: `.venv/bin/python -m wind_agent --config config/demo.json serve`. Не запускать два сервиса на одном порту и каталоге артефактов. Для реального примера выбрать 31 января 2026, 18:00 UTC, обе турбины и 48 часов.

Окружение frontend: Node.js 24.14.0 и npm 11.9.0. Сборка — `npm run build`, локальный просмотр — `npm run preview` на порту 4173. На реальном хостинге `/api` требует отдельного reverse proxy. Альтернатива Streamlit запускается командой `python ui/run.py` после установки `ui/requirements.txt`. Полная инструкция и переменные окружения: [ui/web/README.md](../ui/web/README.md).

После подтверждения полного сценария: улучшить модель на временной валидации, откалибровать интервалы неопределённости и расширить диагностику доступности погодных выпусков. Эффект каждого изменения измерять на одинаковой выборке.

## Материалы, которые нужно иметь перед защитой

- Commit проекта и проверенная инструкция общего запуска.
- Сохранённый CSV запуска и его `run_id` с указанием режима: fixture или реальный архивный прогноз. HTTP-запуск с backend demo также остаётся fixture.
- Исходный погодный ответ и metadata доступности исторического выпуска.
- [Model card](model-card.md), временной split и [отчёт сравнения с baseline](../models/wind-power-v1/validation.json).
- Протокол ручной приёмки из [demo.md](demo.md#ручная-приёмка), включая известные ограничения.

Ответ на вопрос «что готово сейчас» должен опираться на эти артефакты. План, схема архитектуры и демонстрационный график не заменяют доказательство работающего полного цикла.
