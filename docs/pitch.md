# Защита: почасовой прогноз ВЭС

Сценарий на 3 минуты. Перед защитой заменить поля фактически полученными результатами и ссылками на артефакты. Пока измерений нет, произносить «не измерено». Синтетический деморежим подтверждает работу интерфейса; его нельзя представлять как законченный прогноз реальной ВЭС.

HTTP-интеграция с backend `e5da2c6` проверена: шесть сочетаний турбин и горизонтов программным API-клиентом, затем два запуска из браузерного UI. Backend объединён в `main` коммитом `903828a`, включённым в рабочую ветку UI. API с `config/demo.json` возвращает синтетический fixture через настоящий HTTP; эти проверки не подтверждают точность реального прогноза мощности.

## 1. Проблема и результат — 30 секунд

«Для планирования работы ВЭС нужен почасовой прогноз на ближайшие 24–48 часов. Мы строим систему для двух турбин, которая получает архивный прогноз погоды, рассчитывает выработку и показывает, откуда взялся каждый результат. Пользователь выбирает исторический момент выпуска, турбины и горизонт, затем получает график, таблицу и CSV».

Практическая ценность: прогноз и его ограничения находятся рядом. Можно проверить время выпуска, погодный источник, версию модели, качество входов и причину пересчёта, прежде чем использовать результат.

## 2. Как работает система — 45 секунд

```text
Архивный выпуск погоды → проверка временной доступности → признаки
                                                         ↓
История турбин → модель → почасовой прогноз → проверки → API → UI / CSV
                                                ↑
                        новые допустимые входы → новая ревизия
```

«Роль агента — управлять последовательностью действий, проверять доступность входов, обрабатывать сбои и сохранять причину обновления. Числа прогнозирует модель. Для исторического расчёта нельзя использовать сведения из будущего: ограничение относится и к обучению, и к выпуску погоды. Инициализация погодной модели и публикация прогноза — разные моменты».

Эта схема описывает общую систему. Платформа уже содержит API, архивный погодный адаптер и цикл агента; для реального прогноза мощности требуется интеграция модели. Показывать как проверенные вместе только звенья, подтверждённые сохранённым сквозным запуском. UI отображает полученные metadata; сам экран не доказывает корректность архива или обучение без утечки.

## 3. Короткое демо — 60 секунд

1. Назвать источник: **встроенное демо UI**, **HTTP API с backend demo** или **HTTP API с архивным расчётом**. Для API показать `run_id` и режим сервиса. Backend demo обозначить как синтетический fixture, хотя соединение по HTTP настоящее.
2. Выбрать выпуск, турбины и 24 часа. Получить результат, показать состояние агента, график и таблицу. У backend demo единица `fixture_dimensionless`, предупреждение `SYNTHETIC FIXTURE`, а журнал находится в `events`; это тестовая безразмерная величина, не нормализованная мощность. `valid_time` — конец часового интервала.
3. Открыть происхождение данных: время выпуска, погодный run, версию модели, cutoff обучения, предупреждения и ревизию.
4. Показать экспорт CSV. Кнопка «Повторить расчёт» во встроенном деморежиме UI показывает искусственную ревизию. Backend при одинаковых входах сохраняет ID и ревизию — это подтверждено в шести HTTP-сценариях. Сквозное обновление допустимых входов с созданием новой ревизии пока не проверено.

Подробные шаги и сценарии сбоев: [docs/demo.md](demo.md).

## 4. Качество и ограничения — 30 секунд

| Показатель / подтверждение | Фактическое состояние |
| --- | --- |
| API-клиент → HTTP → backend demo (`e5da2c6`) | 6 сочетаний: каждая турбина / обе × 24/48 ч; все `completed`, ревизия 1; CSV проверен, повтор сохранил ID и ревизию |
| Браузерный UI → HTTP API → backend demo | 48 ч / обе: 96 строк; 24 ч / первая: 24 строки; оба запуска `completed`, ревизия 1 |
| Проверки UI с необязательными зависимостями | 46 тестов прошли; `ruff check ui tests/ui` прошёл |
| Общие тесты только с зависимостями backend | 115 прошли, 10 Streamlit AppTest пропущены; полный UI отдельно проверен выше |
| Период временной валидации и состав выборки | Не измерено / не зафиксировано |
| Baseline: MAE, RMSE и единицы цели | Не измерено |
| Модель: MAE, RMSE на той же выборке | Не измерено |
| Ошибка отдельно по горизонтам 24/48 часов | Не измерено |
| Изменение относительно baseline | Не измерено |
| Время полного реального расчёта | Не измерено |
| Покрытие replay февраля реальным прогнозом ВЭС и число успешных выпусков | Не измерено |
| Test-метрики февраля 2026 | Не измерено; требуют предоставленного факта |
| Подтверждённая доступность каждого погодного выпуска | Требует provenance и проверки backend |

«Мы не рисуем фактическую выработку февраля и не заявляем test-точность без предоставленных наблюдений. Validation-оценку показываем с периодом, baseline и единицами. Нормализованную мощность не называем MW/MWh. Отсутствующие калиброванные интервалы не заменяем декоративной полосой на графике».

Протокол с `run_id`, версиями Python и командами: [demo.md](demo.md#протокол-проверки--23-сентября-2026). CSV проверен программным API-клиентом; в браузере проверено нажатие кнопки, сохранение файла на диск не подтверждено.

## 5. Воспроизводимость и следующий шаг — 15 секунд

«UI запускается в отдельном окружении командой `python ui/run.py` после установки зависимостей. Его можно проверить на явно обозначенном встроенном fixture без аккаунта автора. Backend запускается отдельно командой `python -m wind_agent --config config/demo.json serve`. Проверены Python 3.14.3 для UI и 3.11.16 для backend. HTTP-интеграция на синтетических данных работает; реальный прогноз требует подключённой модели и допустимых архивных входов».

После подтверждения полного сценария: улучшить модель на временной валидации, откалибровать интервалы неопределённости и расширить диагностику доступности погодных выпусков. Эффект каждого изменения измерять на одинаковой выборке.

## Материалы, которые нужно иметь перед защитой

- Commit проекта и проверенная инструкция общего запуска.
- Сохранённый CSV запуска и его `run_id` с указанием режима: fixture или реальный архивный прогноз. HTTP-запуск с backend demo также остаётся fixture.
- Исходный погодный ответ и metadata доступности исторического выпуска.
- Model card, описание временного split и отчёт сравнения с baseline, если они готовы.
- Протокол ручной приёмки из [demo.md](demo.md#ручная-приёмка), включая известные ограничения.

Ответ на вопрос «что готово сейчас» должен опираться на эти артефакты. План, схема архитектуры и демонстрационный график не заменяют доказательство работающего полного цикла.
