# Анализ прогноза и следующее действие агента

После проверки почасовой сетки агент анализирует результат, сохраняет `analysis.json`
рядом с прогнозом конкретной ревизии и записывает отчёт в журнал. API возвращает его
через `GET /runs/{run_id}/analysis`; JelAI показывает блок «Анализ агента» для текущей
ревизии. Все числа прогноза и исходные предупреждения модели сохраняются.

## Диагностика

- Для каждой турбины: минимум, максимум и среднее прогноза, самый большой скачок
  между соседними часовыми интервалами с обеими метками времени, диапазон скорости
  ветра в использованном выпуске.
- Флаг постоянного прогноза: не менее 24 последовательных одинаковых часовых
  значений. Это повод проверить входы или режим оборудования; постоянная выработка
  может быть правильной, поэтому агент не заменяет и не обрезает прогноз.
- При новой ревизии: общие ключи «турбина/час», число изменившихся значений, среднее
  и максимальное абсолютное изменение. Разные единицы не сравниваются. Эти числа
  показывают изменение прогноза, а не ошибку относительно фактической выработки.
- Сохраняются предупреждения модели и источника. Fixture явно обозначается;
  результаты разных турбин не суммируются без подтверждённого масштаба.

`model_warnings` всегда содержит все исходные предупреждения. Дополнительные поля
разделяют их без удаления или изменения текста:

- `methodology_warnings`: только точные известные постоянные оговорки поставленной
  модели: некалиброванные интервалы, предварительные временные соглашения SCADA,
  неподтверждённая нормализация, ограничения метаданных архива и единиц мощности.
  Эти ограничения остаются видимыми и не считаются решёнными.
- `review_warnings`: все остальные предупреждения, включая новое или изменённое
  сообщение. Совпадение по подстроке не используется.

`decision=review_required` и `next_action=review_inputs` выдаются при `review_warnings`,
синтетическом источнике, постоянном прогнозе или недостаточных данных для диагностики.
Причины перечислены в `reasons`. Постоянные методологические оговорки сами по себе
не создают эту рекомендацию. При отсутствии обнаруженных поводов проверки выдаётся
`monitor_updates`; `decision_basis` явно поясняет, что это не подтверждение точности,
безопасности или устранения методологических ограничений. Оба решения рекомендательные:
monitor продолжает проверять обновления и записывает решение анализа в свой журнал.

У скачков и изменений не задан произвольный порог опасности: нормализация мощности
не подтверждена, калиброванных порогов нет. Без февральского факта анализ не заявляет
MAE, «точность», экономию или качество доверительного интервала. Он не выбирает новую
модель по holdout и не запрашивает будущую погоду для исторического issue_time.

## Совместимость и проверка

Повтор с неизменёнными входами сохраняет номер ревизии и байты прогноза. Для старой
ревизии без `analysis.json` API читает её сохранённые прогноз и погоду, вычисляет
диагностику в памяти и не изменяет старые файлы. То же правило применяется к старому
`analysis.json` без полей классификации предупреждений: прогноз, входы и сохранённый
отчёт остаются неизменными, API возвращает актуальную классификацию. Отчёт содержит `run_id`, `revision`
и `issue_time`; UI отвергает отчёты другой ревизии.

```sh
python -m pytest tests/agent/test_analysis.py tests/api/test_analysis_api.py tests/agent/test_monitor.py -q
python scripts/verify_agent_monitor.py
```

Вторая команда проверяет настоящий GFS и поставленную модель с явными историческими
часами в отдельном каталоге. Она не изменяет пакет модели и опубликованные результаты
февральского replay. Подробности автономного запуска — [agent-monitor.md](agent-monitor.md).
